# 3. Persistence

## Goal

Persons are stored in Firebase Cloud Firestore by default, a free document database. PostgreSQL is available as an alternative selected by configuration, with the same API behavior. Switching storage does not change the API.

## Requirements

### Storage selection

- **DB-1** Without configuration the application MUST use Firestore. With the Spring profile `postgres` it MUST use PostgreSQL instead.
- **DB-2** In Firestore mode the application MUST start without any PostgreSQL configuration or connection (no data source, JPA or Flyway initialized). In PostgreSQL mode it MUST start without any Firestore configuration.
- **DB-3** The business logic MUST depend on one storage-neutral repository contract (find all sorted, find by id, check e-mail taken by another id, save, delete); each storage provides its own implementation.

### Identity

- **DB-4** Ids MUST be generated by the application as random UUID strings, identically for both storages, so a record keeps its id if data is moved between them.

### Firestore

- **DB-5** Persons are documents in the collection `persons`; the document id is the person id. The collection is created implicitly by the first write.
- **DB-6** Document fields: `firstName`, `lastName`, `email`, `phoneNumber` (strings), `dateOfBirth` (ISO date string), `createdAt`, `updatedAt` (Firestore timestamps).
- **DB-7** Timestamps MUST be truncated to microseconds before saving, because Firestore stores microsecond precision; a value returned on create MUST equal the value read later.
- **DB-8** Sorting by last and first name is done in memory, to avoid requiring a composite index.
- **DB-9** E-mail uniqueness is checked with a query before writing (Firestore has no unique constraints).
  - Accepted risk: two concurrent requests with the same new e-mail may both succeed.
- **DB-10** Connection settings:
  - project id from `GOOGLE_CLOUD_PROJECT`;
  - credentials from the service account key file referenced by `GOOGLE_APPLICATION_CREDENTIALS`;
  - when `FIRESTORE_EMULATOR_HOST` is set, the emulator at that address MUST be used instead, without credentials.

### PostgreSQL

- **DB-11** The schema MUST be created by a Flyway migration; Hibernate only validates it (`ddl-auto: validate`).
- **DB-12** Table `persons`:

  | Column | Type |
  |---|---|
  | `id` | `VARCHAR(36)` primary key |
  | `first_name`, `last_name` | `VARCHAR(100) NOT NULL` |
  | `email` | `VARCHAR(255) NOT NULL UNIQUE` |
  | `date_of_birth` | `DATE NOT NULL` |
  | `phone_number` | `VARCHAR(30) NOT NULL` |
  | `created_at`, `updated_at` | `TIMESTAMP NOT NULL` |

- **DB-13** E-mail uniqueness is checked before writing (case-insensitive) and additionally enforced by the unique constraint.
- **DB-14** Connection from `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`; JDBC time zone UTC.

## Acceptance criteria

| # | Given | When | Then |
|---|---|---|---|
| AC-1 | no profile, no PostgreSQL available | the application starts | it starts and `/actuator/health/liveness` is `200` |
| AC-2 | the same API test suite (see [specification 1](01-person-management.md)) | it runs against the Firestore emulator and against PostgreSQL | all tests pass for both storages |
| AC-3 | Firestore mode, empty database | a person is created | a document `persons/<id>` exists with the fields from DB-6 |
| AC-4 | PostgreSQL mode, empty database | the application starts | Flyway creates `persons` as in DB-12 and Hibernate validation passes |
| AC-5 | either storage | a person is created and read back | `createdAt` and `updatedAt` are identical in both responses |

## Out of scope

- Data migration between Firestore and PostgreSQL.
- Running both storages at the same time, caching, transactions spanning several persons.
