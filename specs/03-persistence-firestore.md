# 3. Persistence: Firestore (default)

## Goal

Persons are stored in Firebase Cloud Firestore, a free document database. Firestore is the default storage; PostgreSQL is an optional alternative described in [specification 4](04-persistence-postgresql.md). Switching storage does not change the API.

## Storage contract

These requirements apply to every storage, including PostgreSQL.

- **DB-1** Without configuration the application MUST use Firestore. Other storages are selected with a Spring profile (PostgreSQL: `postgres`).
- **DB-2** The application MUST start with only the selected storage configured: in Firestore mode no data source, JPA or Flyway is initialized, and the other way round.
- **DB-3** The business logic MUST depend on one storage-neutral repository contract (find all sorted, find by id, check e-mail taken by another id, save, delete); each storage provides its own implementation.
- **DB-4** Ids MUST be generated by the application as random UUID strings, identically for every storage, so a record keeps its id if data is moved between storages.

## Firestore requirements

- **FS-1** Persons are documents in the collection `persons`; the document id is the person id. The collection is created implicitly by the first write.
- **FS-2** Document fields: `firstName`, `lastName`, `email`, `phoneNumber` (strings), `dateOfBirth` (ISO date string), `createdAt`, `updatedAt` (Firestore timestamps).
- **FS-3** Timestamps MUST be truncated to microseconds before saving, because Firestore stores microsecond precision; a value returned on create MUST equal the value read later.
- **FS-4** Sorting by last and first name is done in memory, to avoid requiring a composite index.
- **FS-5** E-mail uniqueness is checked with a query before writing (Firestore has no unique constraints).
  - Accepted risk: two concurrent requests with the same new e-mail may both succeed.
- **FS-6** Connection settings:
  - project id from `GOOGLE_CLOUD_PROJECT`;
  - credentials from the service account key file referenced by `GOOGLE_APPLICATION_CREDENTIALS`;
  - when `FIRESTORE_EMULATOR_HOST` is set, the emulator at that address MUST be used instead, without credentials.

## Acceptance criteria

| # | Given | When | Then |
|---|---|---|---|
| AC-1 | no profile, no PostgreSQL available | the application starts | it starts and `/actuator/health/liveness` is `200` |
| AC-2 | the same API test suite (see [specification 1](01-person-management.md)) | it runs against the Firestore emulator and against PostgreSQL | all tests pass for both storages |
| AC-3 | empty database | a person is created | a document `persons/<id>` exists with the fields from FS-2 |
| AC-4 | a person was created | it is read back | `createdAt` and `updatedAt` are identical in both responses |

## Out of scope

- Data migration between storages.
- Running several storages at the same time, caching, transactions spanning several persons.
