# agent-ai-spring-boot

`agent-ai-spring-boot` is a Spring Boot 3 application that exposes a secured REST API for managing people. It persists data in Firebase Cloud Firestore by default or optionally in PostgreSQL, protects API endpoints with OAuth2 client credentials and JWT bearer tokens, and includes local and Kubernetes deployment assets.

## Prompt

```text
Create the application that exposes a REST API and connects to a PostgreSQL database in the current directory.
The application should have a Person entity with an id and typical fields for each person.
All REST endpoints should be protected with JWT and OAuth2.
The codebase should use Skaffold to deploy on Kubernetes.
Don’t create a plan. 
Don’t ask for confirmation, just continue.
```

## Features

- REST API under `/api/v1/persons` (listing persons is public, other operations require a token)
- Firebase Cloud Firestore persistence by default (document database, free Spark plan); the Firestore emulator is used locally and in tests
- Optional PostgreSQL persistence with Flyway migrations, enabled with the `postgres` Spring profile
- OAuth2 authorization server and JWT resource server in one application
- Health probes for Kubernetes
- Docker Compose for local development
- Skaffold and Kubernetes manifests for cluster deployment
- Positive and negative integration tests with JUnit 5, MockMvc and the Firestore emulator (Testcontainers)
- CircleCI pipeline: tests, image publishing to GitHub Container Registry and deployment to Render

## Prerequisites

- Java 21
- Maven 3.9+
- Docker and Docker Compose
- Kubernetes cluster with `kubectl`
- Skaffold

## Run Locally

Start the Firestore emulator:

```bash
docker compose up -d firestore
```

Run the application against the emulator:

```bash
FIRESTORE_EMULATOR_HOST=localhost:8081 mvn spring-boot:run
```

### Using PostgreSQL instead of Firestore

The storage is selected with Spring profiles: without a profile the application uses Firestore, with the `postgres` profile it uses PostgreSQL (`SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`) and runs Flyway migrations from `src/main/resources/db/migration`.

```bash
docker compose --profile postgres up -d postgres
mvn spring-boot:run -Dspring-boot.run.profiles=postgres
```

In both storages person ids are UUID strings generated by the application.

## Obtain a Token

Request an OAuth2 access token using the configured client:

```bash
curl -u person-api-client:changeit \
  -X POST http://localhost:8080/oauth2/token \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'grant_type=client_credentials&scope=person.read%20person.write'
```

Use the returned `access_token` as a bearer token:

```bash
curl http://localhost:8080/api/v1/persons \
  -H "Authorization: Bearer ${TOKEN}"
```

## API Examples

Create a person:

```bash
curl -X POST http://localhost:8080/api/v1/persons \
  -H "Authorization: Bearer ${TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{
    "firstName": "Jane",
    "lastName": "Doe",
    "email": "jane.doe@example.com",
    "dateOfBirth": "1990-05-20",
    "phoneNumber": "+48123456789"
  }'
```

List people:

```bash
curl http://localhost:8080/api/v1/persons \
  -H "Authorization: Bearer ${TOKEN}"
```

## Build and Test

```bash
mvn clean verify
```

The same integration tests run against both storages: `FirestorePersonControllerIntegrationTest` starts the Firestore emulator and `PostgresPersonControllerIntegrationTest` starts PostgreSQL (with the Flyway migrations) using Testcontainers, so Docker must be running. If `FIRESTORE_EMULATOR_HOST` or `SPRING_DATASOURCE_URL` is set, the tests use that emulator or database instead (CircleCI runs both as service containers).

## Docker Compose

Run the full stack locally with Firestore (default):

```bash
docker compose up --build
```

Or with PostgreSQL:

```bash
SPRING_PROFILES_ACTIVE=postgres docker compose --profile postgres up --build
```

## Kubernetes with Skaffold

Deploy to the current cluster context:

```bash
skaffold run
```

For an iterative development loop:

```bash
skaffold dev
```

The Kubernetes manifests are stored in `k8s/`. In the cluster the application uses the external Firebase Cloud Firestore by default. Before the first deployment create a secret with the Firebase project id and the service account key (see [One-time setup](#one-time-setup) for how to get the key); it is not stored in the repository:

```bash
kubectl create secret generic firebase-credentials \
  --from-literal=project-id=<firebase-project-id> \
  --from-file=firebase-key.json=/path/to/firebase-key.json
```

Skaffold also deploys PostgreSQL. To use it instead of Firestore uncomment `SPRING_PROFILES_ACTIVE: postgres` in `k8s/app-secret.yaml`; the `firebase-credentials` secret is then not needed.

## CI/CD with CircleCI and Render

The project uses Maven [CI-friendly versions](https://maven.apache.org/maven-ci-friendly.html): `pom.xml` contains `${revision}`, which defaults to `1.0.0-SNAPSHOT` for local builds. CircleCI sets it to `1.0.<pipeline number>` (MAJOR.MINOR comes from the `REVISION` variable in `.circleci/config.yml`), and the image is additionally tagged with that version.

The pipeline in `.circleci/config.yml` runs:

1. `build` – `mvn clean verify` against the Firestore emulator and PostgreSQL on every branch.
2. `publish-image` – builds the image with Jib and pushes it to `ghcr.io/<github-user>/agent-ai-spring-boot` with the commit SHA, version and `latest` tags (`master` only).
3. `deploy` – calls the Render Deploy Hook, so Render pulls `latest` and restarts the service (`master` only).

### One-time setup

1. Create a GitHub personal access token (classic) with the `write:packages` scope.
2. Run the pipeline once so the image appears in GitHub Packages, then either make the package public or add registry credentials in Render.
3. Prepare Firestore:
   1. In the [Firebase console](https://console.firebase.google.com) create a project (the free Spark plan is enough) and create a Firestore database in Native mode.
   2. In Project settings → Service accounts click **Generate new private key** and download the JSON file. Do not commit it.
4. In Render create a Web Service from the existing image `ghcr.io/<github-user>/agent-ai-spring-boot:latest`. Add the JSON key as a Secret File named `firebase-key.json` (Render mounts it at `/etc/secrets/firebase-key.json`) and set these environment variables:

   | Variable | Value |
   |---|---|
   | `PORT` | `8080` |
   | `GOOGLE_CLOUD_PROJECT` | Firebase project id |
   | `GOOGLE_APPLICATION_CREDENTIALS` | `/etc/secrets/firebase-key.json` |
   | `APP_SECURITY_ISSUER` | public service URL, e.g. `https://agent-ai-spring-boot.onrender.com` |
   | `APP_SECURITY_CLIENT_ID` | OAuth2 client id |
   | `APP_SECURITY_CLIENT_SECRET` | OAuth2 client secret (do not use `changeit`) |

   To use a Render PostgreSQL database instead, skip the Firestore steps and set `SPRING_PROFILES_ACTIVE=postgres`, `SPRING_DATASOURCE_URL` (`jdbc:postgresql://<host>:5432/<database>`), `SPRING_DATASOURCE_USERNAME` and `SPRING_DATASOURCE_PASSWORD`.

5. Copy the service Deploy Hook URL from Render (Settings → Deploy Hook).
6. In CircleCI (Project Settings → Environment Variables) add:
   - `GHCR_TOKEN` – the GitHub token from step 1,
   - `RENDER_DEPLOY_HOOK_URL` – the Deploy Hook URL from step 5.

### Updating an existing Render deployment

Versions before Firestore support used PostgreSQL only. The image without a profile now uses Firestore, and its health endpoints stay green even without Firestore credentials, so a deploy from `master` would succeed while every `/api/v1/persons` request fails. Before merging into `master`, configure the Render service for one of the storages:

- **Firestore:** add the Secret File `firebase-key.json` and the `GOOGLE_CLOUD_PROJECT` and `GOOGLE_APPLICATION_CREDENTIALS` variables (step 4 above); the `SPRING_DATASOURCE_*` variables can be removed.
- **PostgreSQL:** set `SPRING_PROFILES_ACTIVE=postgres` and drop the `persons` and `flyway_schema_history` tables in the Render database (the `V1` migration changed, so Flyway refuses to start otherwise; existing data is lost).

### Switching between storages

Person ids are UUID strings generated by the application in both storages, so records keep their ids if data is moved between them. Data is not copied automatically when the profile is changed. If a PostgreSQL database was created by an older version with numeric ids, drop the `persons` and `flyway_schema_history` tables so that Flyway recreates the schema.
